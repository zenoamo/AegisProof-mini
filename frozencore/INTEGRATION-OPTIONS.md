# Statement と Guest の接続案

この文書は比較だけである。どの方式も実装していない。guest の証明鍵は無く、statement 回路は guest を再実行しない。

## 実装前仕様での位置

2026-10-09 の実装前仕様は、A を第一候補にし、両方の証明を必須とする。B と C は選んでいない。仕様の本文は `GUEST-INDEPENDENT-VERIFICATION.md` である。

現行の guest 回路は命令列を秘密入力のままにしている。A をその回路のまま実装しても、既定命令列を回路で制約する、という決定は満たさない。命令列の固定は guest 回路の変更であり、そのソースが仕様と一致するまで guest の鍵は作らない。Statement の鍵は流用しない。

現状の対応は次のとおりである。

- guest の公開信号は `zkvmProgramId`、`inputRoot`、`outputCommitment`、`executionId` である。
- 入力と出力の Poseidon ドメイン 19、20、22 は statement と同じ数である。プログラム ID のドメイン 33 も、API の `guestProgramId` と同じである。
- statement はこれらの値を公開入力、またはそのハッシュの前像として束縛する。命令列は見ない。
- API は、既定の 4 命令の結果と ID を witness に入れてから statement を証明する。これは guest 証明の検証ではない。

## A. 二つの証明を別々に検証する

guest と statement の Groth16 をそれぞれ作り、両方を検証する。公開の四つが一致することを、検証処理が追加で見る。

保証は、guest 回路の実行と、statement の束縛が、同じ四つの公開値を指すことである。一つの証明にはならない。

回路は変えない。guest 用の ptau、zkey、検証鍵が新たに要る。既存の `statement.zkey` は上書きしない。検証は二回になる。運用は、二つの成果物と、四つが一致しないときの失敗条件を持つ。

## B. 実行制約を statement に入れる

guest の 4 ステップを statement 回路へ写す。一つの Groth16 が実行と束縛の両方を見る。

保証は一つの証明に入る。対象は今の 4 命令のままで、汎用の ZKVM にはならない。

statement 回路が変わる。いまの R1CS と `statement.zkey` は使えず、新しいセレモニーが要る。guest ファイルを残すなら、二重に保守する。検証処理は一つの証明で済む。回路は大きくなる。

## C. 再帰または集約

statement の中、または第三の回路で、guest 証明を検証する。

保証は、一つの証明が guest 証明の検証結果と statement の束縛を含む、という形にできる。このリポジトリにはその検証回路が無い。費用、制約数、証明システムは未評価である。新しい回路と新しい鍵が要り、開発用の statement 鍵は使えない。運用は A と B より重い。脅威モデルが単一証明を要求するまで始めない。

## 比較

| | A. 独立検証 | B. 回路へ組み込み | C. 再帰・集約 |
| --- | --- | --- | --- |
| 保証 | 二つの証明と公開値の一致 | 一つの証明の中の 4 命令 | 未評価。単一証明に guest 検証を含め得る |
| statement 回路 | 変えない | 変える | 変えるか、別回路を足す |
| 既存の statement 鍵 | 残せる | 無効になる | 無効になる |
| 新しい鍵 | guest 用 | statement の作り直し | 再帰用を含む |
| 検証 | 二回と一致検査 | 一回 | 未評価 |
| 複雑さ | 成果物が二つ | 回路が一つに増える | 最も重い |

接続に必要なのは、選んだ方式での公開値の対応、失敗条件、テストである。A を選んでも、guest の鍵ができるまでは接続済みとは扱わない。B または C を選ぶときは、回路変更と成果物の再生成を別パスで行う。
